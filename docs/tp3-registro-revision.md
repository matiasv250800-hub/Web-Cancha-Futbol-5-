## Checklist de revisión (Bloque D) – lo completa quien revisa

| N.º | Pregunta | Cumple / No cumple | Comentario concreto |
|---|---|---|---|
| 1 | ¿Los nombres de variables, funciones y clases comunican con claridad su propósito? | | |
| 2 | ¿Las funciones hacen una sola cosa, o mezclan varias responsabilidades sin necesidad? | | |
| 3 | ¿Hay lógica duplicada que podría unificarse en un solo lugar (DRY)? | | |
| 4 | ¿Se agregó complejidad para un caso que nadie pidió todavía (YAGNI)? | | |
| 5 | ¿Agregar un comportamiento nuevo obligó a modificar código existente que ya funcionaba, cuando podría haberse extendido sin tocarlo (OCP)? | | |
| 6 | ¿Una subclase respeta el contrato de su clase base, o lo rompe en algún caso (LSP)? | | |
| 7 | ¿Hay dependencias directas a una implementación concreta que podrían depender de una abstracción (DIP)? | | |
| 8 | ¿Los comentarios explican decisiones no obvias, o solo repiten lo que el código ya dice? | | |

> Una buena observación es concreta, accionable y explica el porqué. Se evalúa el código, no a la persona.
